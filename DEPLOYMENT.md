# MMS Deployment Guide — GitHub + Neon + Render

This build is prepared for the same deployment pattern used for OMS:

**Public GitHub repository → Neon PostgreSQL → Render Web Service**

The GitHub repository can be public. Database credentials, Django secrets, administrator passwords, real company records, uploaded media, and backup files must remain private.

## 1. Publish the code to GitHub

Recommended repository name:

`market-management-system-mms`

Create an empty **Public** repository on GitHub, then from the project root run:

```bash
git init
git add .
git commit -m "Initial public MMS release"
git branch -M main
git remote add origin https://github.com/YOUR-USERNAME/market-management-system-mms.git
git push -u origin main
```

Before pushing, run:

```bash
git status
```

Verify that no `.env`, `db.sqlite3`, media uploads, `.mmsbackup` files, Excel exports, CSV exports, or real company data are staged.

## 2. Create the Neon PostgreSQL database

1. Sign in to Neon and create a new project, for example `mms-portfolio`.
2. Use the default database/branch unless you need a different layout.
3. Copy the PostgreSQL connection string from Neon.
4. Keep `sslmode=require` in the connection string.
5. Do **not** place this URL in GitHub or any committed file.

It will look conceptually like:

```text
postgresql://USER:PASSWORD@HOST/DBNAME?sslmode=require
```

The actual value is private and will be stored as Render's `DATABASE_URL` environment variable.

## 3. Create the Render Web Service

You can either use the included `render.yaml` Blueprint or configure the service manually.

### Option A — Render Blueprint

1. In Render, create a new Blueprint.
2. Connect the public GitHub repository.
3. Render reads `render.yaml` from the repository root.
4. Provide the environment variables marked as `sync: false`.

### Option B — Manual Render setup

Create a new **Web Service** from the GitHub repository with:

- Runtime: `Python`
- Branch: `main`
- Build Command: `bash build.sh`
- Start Command: `bash start.sh`
- Health Check Path: `/accounts/login/`
- Plan: Free is suitable for temporary portfolio/UAT testing

## 4. Render environment variables

Add the following private variables in Render:

```text
DATABASE_URL=<your Neon connection string>
MMS_ADMIN_USERNAME=<your private admin username>
MMS_ADMIN_PASSWORD=<a strong private password>
MMS_ADMIN_EMAIL=<optional email>
DJANGO_DEBUG=False
DJANGO_SECURE_SSL_REDIRECT=True
DJANGO_TIME_ZONE=Asia/Kabul
```

`DJANGO_SECRET_KEY` can be generated by Render when using the included `render.yaml`. If configuring manually, create a long random secret and add it as:

```text
DJANGO_SECRET_KEY=<long-random-secret>
```

You normally do not need to set `DJANGO_ALLOWED_HOSTS` or `DJANGO_CSRF_TRUSTED_ORIGINS` for the default Render URL. MMS automatically trusts Render's `RENDER_EXTERNAL_HOSTNAME`.

## 5. What happens on deploy

`build.sh`:

1. upgrades pip;
2. installs `requirements.txt`;
3. collects static files for WhiteNoise.

`start.sh`:

1. runs Django migrations against Neon;
2. ensures the baseline MMS roles/settings exist without overwriting later admin customizations;
3. creates the initial System Admin from private environment variables if it does not already exist;
4. starts Gunicorn.

The admin bootstrap does **not** reset an existing administrator's password on later deploys.

## 6. Do not seed public demo credentials

Do not run this command on the public Render deployment:

```bash
python manage.py seed_demo --with-demo-data
```

That command creates predictable local demonstration accounts. It is intended only for local testing.

The production startup does **not** run the demo seeder. It uses `ensure_admin_from_env`, which creates only missing baseline roles/settings and the first private System Admin.

## 7. Uploaded logos and profile pictures on Render Free

MMS supports uploaded company logos and employee profile pictures, but Render Free uses an ephemeral filesystem. Uploaded files can disappear after a restart, redeploy, or free-service spin-down.

For this temporary portfolio deployment, that limitation is acceptable if uploads are treated as temporary. For persistent uploads later, use one of these approaches:

- upgrade the Render service and attach a persistent disk, or
- move uploaded media to an object-storage service.

The Neon database remains persistent independently of Render's local filesystem.

## 8. First live test

After Render reports a successful deployment:

1. open the generated `https://<service-name>.onrender.com` URL;
2. sign in with `MMS_ADMIN_USERNAME` / `MMS_ADMIN_PASSWORD`;
3. confirm Dashboard, Zones, Customers, Products, Record Sale, Reports, Excel export, Backup, and Help;
4. create test users for each role using synthetic data;
5. verify the zone daily dispatch and sale numbering rules;
6. test Cases/Cash switching and the Daily Sales Report Excel sheet.

## 9. Security before sharing the portfolio link

- Use synthetic data only.
- Never upload a real company backup to a public demo.
- Keep `DEBUG=False`.
- Keep the Neon connection string private.
- Keep the System Admin password private.
- Do not publish customer names, phone numbers, addresses, or real sales.
- Rotate credentials immediately if they are ever committed to Git history.

## 10. Updating the deployed application

After the GitHub repository is connected to Render, ordinary updates are:

```bash
git add .
git commit -m "Describe the MMS update"
git push origin main
```

Render can automatically deploy the new commit. The Neon database remains the same, and `start.sh` applies new Django migrations automatically.
